# Звіт до практичної роботи №39

**Тема:** виокремлення бізнес-логіки в сервісний рівень.

## Що реалізовано

Створено папки Dtos, Services і Mappings. Доменна модель Posting зберігає внутрішні дані; PostingPostDto визначає лише дані створення без Id, CreatedAt і Price; PostingPutDto додає Id та ціну контракту редагування; PostingGetDto містить усі вихідні поля.

PostingMapper перетворює вхідні DTO в Posting та Posting у DTO відповіді. Він лише копіює дані, без HTTP-статусів, збереження або розрахунків.

PostingService реалізує IPostingService і містить усі операції зі списком, генерацію Id, присвоєння UTC-часу, перевірки даних та розрахунок ціни. Метод Update додатково отримує Id зі шляху, щоб узгодження маршруту й DTO перевіряв сервіс. Обробники викликають лише сервіс і мапер, а також обирають належну HTTP-відповідь.

Сервіс зареєстровано через `AddScoped<IPostingService, PostingService>()` до `Build()`. Статичний список зберігає записи між запитами незалежно від створення нового Scoped-екземпляра; доступ до нього синхронізовано.

## Розширене бізнес-правило

У DTO створення поля Price немає. Create автоматично визначає ціну за фактичною вагою й способом доставки. Конкретних тарифів у документі не задано, тому використано явне навчальне припущення: Department = 40 + 10 × Weight, Courier = 80 + 15 × Weight, ExpressCourier = 120 + 24 × Weight. Це тарифи з попередньої роботи, а не обов’язкові числа з ПР-39.

Формули містяться в сервісі. POST-обробник має однакові кроки незалежно від них: DTO → модель → Create → DTO відповіді → 201. Зміна формули не потребує зміни обробника.

## Фактичні перевірки

Збірка сервера й перевірок пройшла з **0 помилок і 0 попереджень**. Усі **18/18** перевірок сервісу, мапера, DI та реального HTTP-сервера успішні, див. [checks-output.txt](checks-output.txt).

| Сценарій | Підтверджений результат |
| --- | --- |
| POST: 2 кг, Department, Price не передано | 201, Price = 60 |
| POST: 2 кг, Courier | 201, Price = 110 |
| POST: 2 кг, ExpressCourier | 201, Price = 168 |
| POST із зайвими price=0.01, id=999999 і старим createdAt | Повертаються серверні Id/час і Price = 60 |
| GET після створення | Запис і розрахована ціна збережені між HTTP-запитами |

| POST із вагою 0 | 400, errors.Weight від сервісу |

Додатково виконано перший POST саме з [requests.http](../requests.http). Він не містить Price, але сервер повернув 201 та `price: 60`. Повний запит і відповідь: [post-response.txt](post-response.txt). Цей запис отримано HTTP-клієнтом PowerShell; його не подано як результат натискання Send Request у VS Code.

У VS Code файл відкритий, але вікно перебуває в **Restricted Mode**, а редактор показав режим Plain Text. Розширення REST Client встановлене з ПР-38. Підтвердження довіри та доступності розширення залишене для ручної дії користувача; зміни налаштувань довіри автоматично не виконувалися. Тому перевірка саме через кнопку REST Client на цьому етапі не підтверджена. HTTP-контракт і розрахунок незалежно підтверджені реальними запитами.

## Короткий висновок

Розділення DTO, доменної моделі, мапера й сервісу зробило HTTP-обробники незалежними від тарифів та способу зберігання. Нове правило обчислення ціни реалізоване в Create, а стандартний POST-обробник лише передає дані між рівнями. Контракт створення виключає керування службовими полями клієнтом.

## Відповіді на контрольні запитання

1. **Модель бізнес-логіки та DTO — у чому різниця?** Модель представляє сутність усередині застосунку, з якою працює сервіс. DTO визначає зовнішній формат конкретної операції. Тому POST не має службових полів, а GET повертає їх.
2. **Чому клієнт не повинен задавати Id і CreatedAt при створенні?** Сервер гарантує ідентичність запису й достовірний час створення. Зовнішні значення могли б спричинити колізії або підробити історію. Вони генеруються у Create.
3. **Яка роль мапера?** Перетворити поля DTO в модель і модель у DTO. Він ізолює зовнішній формат від внутрішнього та не зберігає записи, не рахує тарифи й не формує HTTP-відповіді.
4. **За що відповідає обробник?** Прийняти дані контракту, передати їх маперу й сервісу, отримати результат та сформувати статус і тіло HTTP. Правила ціни, Id, перевірок і збереження йому не належать.
5. **Де мають бути бізнес-правила?** У PostingService або інших спеціалізованих доменних сервісах. Так вони повторно використовуються та перевіряються без HTTP, а зміна правил не змінює маршрути.
6. **Навіщо IPostingService?** Він задає контракт операцій. Обробник залежить від інтерфейсу, тому реалізацію з пам’яттю можна замінити іншою або тестовою, зберігаючи її контракт.
7. **Що робить AddScoped і коли?** До Build він реєструє відповідність IPostingService → PostingService зі Scoped-часом життя. При запиті залежності контейнер надає об’єкт, спільний у межах поточного scope.
8. **Scoped, Singleton, Transient?** У звичайному HTTP-запиті Scoped — один екземпляр на запит; Singleton — один на контейнер застосунку; Transient — новий при кожному отриманні залежності. Статичні поля є спільними незалежно від часу життя об’єктів, тому Scoped сам по собі не ізолює список.
9. **Як сервіс потрапляє в параметр лямбди?** Minimal API розпізнає зареєстрований тип параметра IPostingService та отримує його зі служб поточного запиту. Розробник не створює конкретний PostingService у маршруті.
10. **Що буде без реєстрації?** Контейнер не зможе надати потрібну залежність. При явному отриманні через GetRequiredService виникне InvalidOperationException. Для ендпойнта збій може проявитися під час побудови/аналізу маршруту або обробки запиту залежно від способу прив’язування; потрібна відповідна реєстрація.

Довідка щодо DI та часу життя: [Microsoft Learn — Dependency injection in ASP.NET Core](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/dependency-injection?view=aspnetcore-10.0).
